# RUNBOOK — راهنمای جامع مدیریت سیستم چند ایجنتی (نسخه ۵.۱)

این مستند نحوه مدیریت چرخه حیات توسعه نرم‌افزار با ایجنت‌های تخصصی را توضیح می‌دهد. در نسخه ۵.۱ تمرکز اصلی روی پایداری چرخه فیدبک (Feedback Loop) و جلوگیری از توهم زدن ایجنت‌هاست.

## ساختار معماری ایجنت‌ها (Multi-Agent Lifecycle)

```
       ┌───────────────────────────────┐
       │   Orchestrator (EXECUTE.md)   │
       │   تخصیص تسک بر اساس مایلستون   │
       └──────────────┬────────────────┘
                      │
        ┌─────────────┴─────────────┐
        ▼                           ▼
┌───────────────┐           ┌───────────────┐
│   Architect   │           │   Developer   │
│ طراحی قرارداد │           │   پیاده‌سازی   │
└───────┬───────┘           └───────┬───────┘
        │                           │
        └─────────────┬─────────────┘
                      ▼
              ┌───────────────┐
              │  QA Engineer  │ ◄───────┐
              │ تست‌نویسی TDD │         │
              └───────┬───────┘         │ Feedback Loop (Max 3)
                      │                 │ (در صورت باگ)
             Pass? ───┼── No ───────────┘
                      │
                     Yes (SUCCESS)
                      ▼
              ┌───────────────┐
              │Security/DevOps│
              │  استقرار و CI │
              └───────────────┘
```

## اصول مهندسی کیت (Non-Negotiable Principles)
1. **اصل تک‌مسئولیتی (SRP):**
   - Developer هرگز تست نمی‌نویسد (جلوگیری از تست جانبدارانه).
   - QA هرگز کدهای بیزنس لاجیک را ویرایش نمی‌کند.
   - Orchestrator فقط DAG تسک‌ها را سازمان‌دهی می‌کند.
2. **قرارداد انتقال ساختاریافته (Strict JSON Handoff):**
   - تمام ارتباطات درون `agent/.state/handoff.json` ذخیره می‌شود.
3. **مکانیزم ضد لوپ (Anti-Looping):**
   - چرخه رفت‌وبرگشت بین QA و Developer به ۳ بار محدود شده است (`qa_retry_count`). اگر کد بعد از ۳ بار پاس نشد، تسک Block می‌شود و انسان باید مداخله کند.
